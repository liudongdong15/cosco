## Findings

### [P1] CCFI `source_url` still is not a reproducible URL or source reference

The schema now includes `source_url`, and `validate_metrics.py` now rejects blank external sources (`scripts/validate_metrics.py:33-36`, `scripts/validate_metrics.py:102-109`). That fixes the empty-field part of the previous finding. However, the CCFI rows still populate `source_url` with descriptive labels rather than a URL, local snapshot path, or command that can reproduce the value, e.g. `交通运输部月度数据+主流机构引述...` and `上海国际海事信息与文献网(SIMIC)` in `data/value_line_metrics_reviewed.csv:2`, `data/value_line_metrics_reviewed.csv:14`, `data/value_line_metrics_reviewed.csv:26`, `data/value_line_metrics_reviewed.csv:38`, `data/value_line_metrics_reviewed.csv:50`, `data/value_line_metrics_reviewed.csv:108`, `data/value_line_metrics_reviewed.csv:129`, `data/value_line_metrics_reviewed.csv:150`, and `data/value_line_metrics_reviewed.csv:171`.

What can go wrong: CCFI is the key external dependency and is now plotted as reviewed data, but a later reviewer still cannot click, fetch, or rerun anything to reproduce the annual average. The validator currently only checks non-empty text, so `source_url=foo` would pass strict validation. This preserves the anti-fabrication gap from the previous review for the most important non-PDF metric.

Suggested fix: make the provenance field semantically enforceable. Either require `source_url` to start with `http://`, `https://`, or `file://`, or rename the field to `source_ref` and add a stricter contract such as `url:...`, `snapshot:...`, or `command:...`. For CCFI annual averages, include the exact SIMIC/交通运输部 URL or a local raw-data snapshot plus the calculation rule.

### [P2] Market data adjustment basis is still contradictory

The generated report says market data is from `akshare 不复权日线` in one place (`reports/cosco_value_line.html:291`) and in the footer (`reports/cosco_value_line.html:321`), but the valuation note says `akshare 前复权日线` (`reports/cosco_value_line.html:297`). The same mismatch exists in the generator (`scripts/build_value_line.py:781` vs `scripts/build_value_line.py:803`). The CSV has the same mixed signal: `source_url` says `adjust='' 不复权日线`, while `evidence_text` still says `前复权年末收盘价` for price rows such as `data/value_line_metrics_reviewed.csv:20-22`.

What can go wrong: PE/PB, yearly high/low, close, market cap, and dividend yield depend on the price basis. A reader cannot know whether the valuation band is adjusted or unadjusted. If future regeneration uses one basis while the report describes another, historical valuation comparability will drift silently.

Suggested fix: choose one basis and make it a single named constant/label used by CSV generation, report copy, and tests. If values are from `akshare.stock_zh_a_daily(symbol='sh601919', adjust='')`, replace all `前复权` evidence/report strings with `不复权`, and add a regression assertion that generated HTML does not contain the opposite basis label.
